Fiche d'intervention

La fiche n'a pas pu être lue : le fichier etat.js manque. Dans le dossier du projet, lance python outils/verifier.py, puis recharge la page.

Le jeu

Tout part du jeu installé sur la console : la cartouche est morte, on travaille sur la copie numérique. Tant qu'elle n'est pas dumpée sur le PC, il n'y a rien à ouvrir dans Ghidra. Le dump reste dans local/, que le dépôt ne publie jamais.

  1. Allume la console en maintenant Start : Luma lance GodMode9.
  2. Appuie sur HOME, choisis « Title manager », puis [A:] SD CARD. La liste des jeux installés s'affiche avec leur nom. (Entrer dans le dossier title avec A ne montre que des dossiers aux noms en chiffres : ce n'est pas le bon chemin.)
  3. Choisis Pokémon X, A, « Manage Title... », puis « Dump CXI/NDS file ». Le fichier .cxi arrive dans 0:/gm9/out, déjà déchiffré. Si une mise à jour du jeu est installée (un titre qui commence par 0004000E), dumpe-la de la même façon : c'est elle qui porte le code qui tourne vraiment.
  4. Éteins, sors la microSD et copie le fichier dans local/dump/ du projet (crée le dossier s'il n'existe pas).
  5. python outils/inspecter.py local/dump/pokemon-x.cxi doit répondre « déchiffré, prêt à extraire ». Recopie l'empreinte SHA-256 dans le journal.
  6. python outils/extraire.py local/dump/pokemon-x.cxi pose le code dans local/extrait/exefs/code.bin, l'en-tête étendu dans exheader.bin, les fichiers dans local/extrait/romfs/, et l'inventaire des GARC dans local/extrait/inventaire.txt. Puis python outils/elfer.py local/extrait/exefs/code.bin en fait un code.elf prêt pour Ghidra.
  7. python outils/verifier.py remet la fiche et ce relevé à jour.

Feuille de route

Sept paliers, chacun relié à un point de test de la carte (TP1 à TP7). Un palier pèse plus lourd quand il demande plus de travail : le pourcentage global en tient compte. Les tâches cochées viennent de etat.json ; verifier.py coche seul celles qu'il peut constater.

    Installer ce qui manque

    1. REA d'abord. Il faut Node 22.19 ou plus récent. Indique-lui notre Ghidra par la variable GHIDRA_INSTALL_DIR (le dossier local/outils/ghidra), puis lance npx -y rea-agents@latest setup dans le même terminal : il montre ce qu'il va écrire et demande confirmation. Relance Claude Code ; /mcp doit montrer rea connecté. Limite : sous Windows, REA 6.4 n'ouvre que des exécutables PE x86 et refuse notre ARM, brut comme en ELF ; il faudra le faire tourner sous WSL (Ubuntu) avec un Ghidra pour Linux. Tout est noté dans outils/REA.md.
    2. ctrtool, makerom, Ghidra. Dépose leurs archives .zip dans local/telechargements/, puis python outils/installer.py : il les déballe dans local/outils/, clone les scripts Ghidra 3DS (git requis) et prépare Jython pour eux.
    3. devkitPro. Son installateur graphique, puis dans le terminal MSYS2 qu'il installe : pacman -S 3ds-dev. Rouvre le terminal pour que DEVKITPRO et DEVKITARM existent.
    4. Azahar s'installe à part. Il ne sert qu'à tracer sans toucher à la console.
    5. Pour finir, python outils/verifier.py constate ce qui est là.

    Ghidra, réglages pour la 3DS

    1. Ghidra 12 ne lance plus Jython par défaut, or les scripts 3DS sont écrits en Python 2. installer.py s'en charge : il déballe l'extension Jython livrée avec Ghidra et pose l'en-tête @runtime Jython sur les quatre scripts.
    2. Lance local/outils/ghidra/ghidraRun.bat. Ghidra veut Java 21. Crée un projet.
    3. Le plus simple : python outils/elfer.py local/extrait/exefs/code.bin écrit code.elf, que File, Import File ouvre directement à 0x00100000, sans réglage.
    4. Sinon, importe code.bin en « Raw Binary », langage ARM:LE:32:v6, et dans Options l'adresse de base 0x00100000 : c'est là que la console charge le code d'un jeu.
    5. Ouvre le programme. Avant d'accepter l'analyse, va en 0x00100000 (touche G), appuie sur D puis F : en binaire brut, Ghidra ne connaît pas le point d'entrée. Lance ensuite l'analyse automatique.
    6. Script Manager, « Manage Script Directories », ajoute local/outils/ghidra-scripts/. Lance les quatre scripts dans cet ordre :
      1. Label3dsSVCs.py nomme les appels système (svc).
      2. Label3dsHandles.py nomme les handles de services. Il exige qu'on ait d'abord nommé à la main ctr::srv::GetServiceHandleDirect la fonction qui demande un handle à srv: (en-tête IPC 0x00050100).
      3. Label3dsCTRFns.py reconnaît les fonctions IPC de la bibliothèque.
      4. Set3dsTlsType.py type la zone de stockage par fil où passent les messages.

    Le détail, les options d'analyse et la ligne de commande : outils/GHIDRA.md.

    Carte du système

    Ce qu'il faut avoir en tête avant d'ouvrir le binaire : qui exécute quoi, à qui le jeu parle, et où les choses tombent en mémoire. Chaque fois que REA affirme « ceci est le service fs:USER », c'est cette carte qui permet de juger si c'est plausible.

    Deux processeurs, et deux coprocesseurs

    ARM11 MPCore2 cœurs à 268 MHz, 4 à 804 MHz sur New 3DS. Fait tourner le jeu et le système Horizon. C'est le seul code qu'on décompile.
    ARM9 (ARM946)134 MHz. Sécurité, NAND, cartouche, chiffrement. C'est lui que boot9strap détourne pour lancer Luma ; le jeu ne le voit jamais.
    GPU PICA200Le jeu ne le commande pas en direct : il passe par le service gsp::Gpu.
    DSPLe son, par le service dsp::DSP.

    Les services que le jeu appelle

    Un jeu ne touche jamais le matériel. Il envoie des messages (IPC) à des services du système, chacun connu par son nom. C'est ce que les scripts Ghidra étiquettent, et c'est ce qu'il faudra fournir sur PC au palier 7.

    fs:USERfichiers : romfs, sauvegarde
    gsp::Gpuécrans et GPU
    hid:USERboutons, écran tactile, gyroscope
    dsp::DSPson
    apt:Uvie de l'application : menu Home, mise en veille
    cfg:uréglages de la console : langue, région
    ptm:ualimentation, batterie, podomètre

    La mémoire vue par le jeu

    AdresseCe qu'on y trouve
    0x00100000Le code du jeu. C'est l'adresse à donner à Ghidra.
    0x08000000Le tas.
    0x10000000La mémoire partagée avec les services. Le sommet de la pile est juste dessous.
    0x14000000Le tas linéaire, que le GPU peut lire. Sur New 3DS, aussi à 0x30000000.
    0x1EC00000Les registres d'entrées-sorties.
    0x1F000000La VRAM, 6 Mo.
    0x1FF80000La configuration partagée par le noyau.
    0x1FF82000Le stockage par fil (TLS), où passent les messages IPC.
    0xFFFF0000Le noyau. Inaccessible au jeu.

    Pokémon X, ce qu'on sait

    Le romfs de Pokémon X est un arbre de dossiers numérotés, a/0/0/0, a/0/0/1 et ainsi de suite. Chaque feuille est un conteneur GARC. La communauté Project Pokémon a déjà cartographié lequel contient quoi ; on s'appuie sur son travail pour écrire nos propres lecteurs.

    FormatCe que c'estChez nous
    GARCLe conteneur. Version 4 pour X et Y. Des fichiers numérotés ; chaque numéro peut porter jusqu'à 32 sous-fichiers, annoncés par un vecteur de bits. Les magics sont écrits à l'envers sur le disque (« CRAG »).Lecteur écrit, outils/garc.py, testé en aller-retour.
    LZ11La compression. Un octet 0x11, puis la taille décompressée sur trois octets, puis des blocs de huit éléments annoncés par un octet de drapeaux.Décompresseur écrit, outils/lz11.py, avec LZ10.
    TextesDe l'UTF-16 chiffré par une clé tournante : elle part de 0x7C89, avance de 0x2983 à chaque ligne et tourne de 3 bits à chaque caractère. Des commandes (0x0010) y glissent les variables et les pauses.Décodeur écrit, outils/texte.py, testé sur des données fabriquées. Reste à le valider sur le romfs.
    TablesStatistiques, types, apprentissages : des enregistrements de taille fixe, un par Pokémon.À écrire au palier 4.
    BCHLes modèles 3D de Game Freak. Références : Ohana3DS et SPICA.Lecteur et rendu dans la Visionneuse BCH de ce site, à valider sur le romfs.

    Pour parcourir le romfs extrait sans écrire une ligne, l'Explorateur de romfs de ce site ouvre les GARC, décompresse, décode les textes et montre les images et les modèles, dans le navigateur, sans que rien ne quitte le PC.

    Ce que « natif sur PC » demande

    Il y a deux voies.

    La décompilation : réécrire tout le jeu en C, jusqu'à ce que ce C, recompilé, redonne le binaire à l'octet près. C'est ainsi qu'ont été faits les portages de jeux N64. Pour un jeu 3DS, personne ne l'a terminée. Le jeu a été compilé avec RVCT, le compilateur d'ARM de l'époque, absent des outils qui comparent le résultat fonction par fonction.

    La recompilation statique : traduire mécaniquement le code ARM11 en C, puis fournir sur PC tout ce que le jeu demande au système. C'est la voie de N64Recomp. L'outil n'existe pas pour la 3DS : il faudrait l'écrire.

    Les paliers 1 à 6 servent aux deux voies. Le choix se fait au palier 7, quand on saura combien de fonctions et de services il y a.

    REA pilote Ghidra à notre place et va vite. On garde Ghidra à la main pour vérifier chacune de ses affirmations : une adresse citée doit exister, une référence croisée doit se retrouver.

    Exercices à vérité connue

    Trois petits homebrews dont on a le code, dans exercices/. On les compile avec make (en -O0), on ouvre le code nu exNN.bin comme un vrai jeu (ARM v6, base 0x00100000), et on retrouve ce qu'il fait. Le .elf, qui garde les noms, sert de corrigé quand on est bloqué. Puis on recommence avec make OPT=-O2 : le même programme, méconnaissable, c'est l'état d'un jeu livré. Tant que REA ne tourne pas sous WSL, on fait les exercices à la main dans Ghidra ; REA sert ensuite à comparer ses réponses aux tiennes, et les blocs « Avec REA » disent quoi lui demander.

    01 La boucle

    Un écran texte, un compteur, Start pour sortir. Tout jeu a cette forme.

    1. Trouve la chaîne « Exercice 01 ». Qui s'en sert ? Remonte de la chaîne à la fonction par ses références.
    2. Décris le prologue et l'épilogue de cette fonction.
    3. Où vit la variable tours ? Pourquoi là ?
    4. Comment reconnaît-on le haut de la boucle ? Descends dans la première fonction appelée jusqu'à une instruction svc.
    5. Que devient (tours & 63) == 0 ?

    Avec REA. Demande à Claude Code :

    Avec REA, ouvre exercices/01-boucle/ex01.bin comme ARM v6 à 0x00100000 et dis-moi quelle fonction appelle printf avec la chaîne « Exercice 01 », avec les preuves.

    La réponse doit citer l'adresse de la chaîne et celle de la fonction, les instructions qui chargent l'adresse et font l'appel, et la liste des références croisées. Ensuite, refais le chemin à la main dans Ghidra : si une adresse ne mène pas où REA le dit, c'est lui qui se trompe.

    Correction
    1. La chaîne est dans les données en lecture seule, avec une seule référence : depuis main. Elle est chargée dans r0 par un ldr qui lit une adresse posée juste après la fonction (la réserve de constantes), puis vient un bl. Ne sois pas surpris d'y voir puts et une chaîne sans retour à la ligne : GCC remplace un printf sans format par puts.
    2. À l'entrée, push {…, lr} range sur la pile les registres que la fonction va abîmer et l'adresse de retour. À la sortie, pop {…, pc} les remet, et charger pc fait le retour.
    3. En -O0, sur la pile, lue et réécrite à chaque tour. En -O2, dans un registre sauvegardé, r4 à r7, parce qu'il survit aux appels : r0 à r3 sont écrasés par toute fonction appelée.
    4. Un bl vers aptMainLoop, puis un test de r0 et un saut vers la sortie s'il vaut zéro ; tout en bas, un saut qui remonte ici. En descendant dans les enveloppes de libctru, on finit sur un svc : 0x32 pour envoyer un message IPC, 0x24 pour attendre un événement.
    5. tst r4, #63 (ou #0x3f), suivi d'un bne qui saute par-dessus l'affichage.

    02 L'aiguillage

    Huit modes qu'on fait tourner avec A, chacun sa formule, choisis par un switch.

    1. Comment la fonction de calcul choisit-elle son cas ? Compare -O0 et -O2.
    2. Retrouve le tableau des huit noms de modes. Qu'y a-t-il dedans ?
    3. Le cas 7 divise par 7. L'ARM11 n'a pas d'instruction de division : que vois-tu à la place ?
    4. Que devient la rotation du cas 4, (x << 5) | (x >> 27) ?

    Avec REA. Demande à Claude Code :

    Avec REA, ouvre exercices/02-aiguillage/ex02.bin comme ARM v6 à 0x00100000, trouve la table de sauts et dis-moi combien de cas elle a et où va chacun, avec les preuves.

    La réponse doit donner l'adresse de la comparaison de bornes, celle de la table, les huit adresses qu'elle contient et le désassemblage cité de chaque cas. Vérifie ensuite dans Ghidra : la table doit avoir huit entrées, ni plus ni moins.

    Correction
    1. Soit une cascade de cmp et de sauts, un test par cas : la forme de -O0. Soit une table de sauts : cmp r0, #7, puis ldrls pc, [pc, r0, lsl #2] qui pioche l'adresse du cas dans une liste de huit mots, et un saut vers le cas par défaut si la valeur dépasse 7. C'est la forme de -O2. Ghidra la reconnaît et réécrit un switch.
    2. Huit mots de 4 octets à la suite, chacun l'adresse d'une chaîne (« plus un », « triple »…). Le code y lit avec ldr rX, [rY, rZ, lsl #2], le mode servant d'index. Dans Ghidra, il faut parfois dire « ceci est un pointeur » pour voir les chaînes.
    3. En -O0, un appel à __aeabi_uidiv, la division de la bibliothèque. En -O2, une multiplication par l'inverse : umull avec la constante 0x24924925, puis quelques décalages.
    4. Une seule instruction : ror de 27. Le compilateur reconnaît la rotation écrite en deux décalages.

    03 La sauvegarde

    Une structure écrite telle quelle sur la carte SD, avec un magic, une version et une somme de contrôle.

    1. Trouve l'appel qui écrit le fichier. Quelle taille passe-t-il ?
    2. Retrouve les champs et leurs décalages à partir des écritures dans la structure.
    3. Le magic vaut 0x56415344. Quels sont les quatre premiers octets du fichier sur la carte SD ?
    4. Reconstruis l'algorithme de la somme de contrôle.
    5. La lecture peut être refusée de trois façons. Lesquelles ?

    Avec REA. Demande à Claude Code :

    Avec REA, ouvre exercices/03-sauvegarde/ex03.bin comme ARM v6 à 0x00100000, trouve la fonction qui calcule la somme de contrôle et réécris-la en C, avec les preuves.

    La réponse doit donner l'adresse de la fonction, la boucle désassemblée et citée (la rotation, la lecture d'octet, la borne de 24) et les références croisées vers l'écriture et la lecture du fichier. Puis vérifie à la main dans Ghidra, et compare son C avec source/main.c.

    Correction
    1. 28 octets (0x1C), passés à fwrite.
    2. magic à 0 (4 octets), version à 4 (2), vies à 6 (1), niveau à 7 (1), nom à 8 (12), score à 20, somme à 24. Aucun remplissage : chaque champ tombe déjà sur son alignement. Les tailles se lisent aux instructions : str pour 4 octets, strh pour 2, strb pour 1.
    3. 44 53 41 56, « DSAV » : la console range l'octet de poids faible en premier. Cherche donc la valeur (Search, For Scalars), pas la chaîne.
    4. On part de 0x1234. Pour chacun des 24 premiers octets : rotation à gauche d'un bit (ror #31), puis on ajoute l'octet (ldrb).
    5. Magic faux (code -1), version différente de 3 (code -2), somme fausse (code -3).
